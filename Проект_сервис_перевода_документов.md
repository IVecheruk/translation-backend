# Сервис перевода документов (DOCX/DOC/PDF) — техническая спецификация

Дипломный проект + MVP стартапа. Команда: 3 человека. Срок: 1–2 месяца.

---

## 1. Идея проекта

Веб-сервис, куда пользователь загружает документ (`.docx`, `.doc`, `.pdf`), выбирает язык перевода, и получает файл на выходе **с сохранённой структурой и форматированием** — это и есть главная сложность и главная ценность продукта (Google Translate и подобные сервисы не всегда качественно сохраняют вёрстку).

---

## 2. Общая архитектура

```
[Frontend: React]
      |
      | REST / WebSocket (статус задачи)
      v
[Java backend: Spring Boot]
   — Auth (JWT)
   — Загрузка/хранение файлов
   — История заказов, статусы
   — Постановка задач в очередь
      |
      | RabbitMQ (задача: file_id, source_lang, target_lang)
      v
[ML-сервис: Python, FastAPI]
   — Парсинг DOCX/DOC/PDF
   — Перевод текста (NLLB-200 / MarianMT)
   — Сборка переведённого файла с исходным форматированием
      |
      v
[Хранилище: S3-совместимое (MinIO) + PostgreSQL]
```

Три независимых сервиса — идеально ложится на трёх человек, каждый работает в своём репозитории/контейнере, взаимодействие через чётко описанный контракт (см. раздел 6).

## 3. Java backend (бизнес-логика)

### Стек
- Spring Boot 3.x, Spring Security (JWT), Spring Data JPA
- PostgreSQL — метаданные пользователей, файлов, заказов
- RabbitMQ (spring-boot-starter-amqp) — очередь задач для ML-сервиса
- MinIO SDK или AWS S3 SDK — хранение самих файлов

### Основные сущности БД
```
users
  id, email, password_hash, created_at

translation_jobs
  id, user_id (FK), 
  source_file_key (путь в S3), 
  result_file_key (путь в S3, nullable),
  source_lang, target_lang,
  status (PENDING | PROCESSING | DONE | FAILED),
  file_format (docx | doc | pdf),
  created_at, updated_at, error_message (nullable)
```

### REST API (примерный список эндпоинтов)
```
POST   /api/auth/register
POST   /api/auth/login                 -> JWT

POST   /api/documents/upload           -> {job_id}
  (multipart: file, source_lang, target_lang)

GET    /api/documents/{job_id}/status  -> {status, progress}
GET    /api/documents/{job_id}/download -> файл

GET    /api/documents/history          -> список заказов пользователя
```

### Логика обработки
1. Пользователь загружает файл → backend кладёт его в MinIO, создаёт запись `translation_jobs` со статусом `PENDING`
2. Backend публикует сообщение в очередь RabbitMQ: `{job_id, file_key, source_lang, target_lang, format}`
3. ML-сервис слушает очередь, забирает задачу, меняет статус на `PROCESSING`
4. После обработки ML-сервис кладёт результат в MinIO и публикует сообщение о завершении (либо просто обновляет статус в БД напрямую — обсудите, кто владеет БД)
5. Фронтенд поллит `/status` или слушает WebSocket

### Что можно не делать в MVP
- Полноценный биллинг/подписки — достаточно заглушки "бесплатных N переводов"
- Сложные роли/права — только обычный пользователь

## 4. ML-сервис (Python)

### Стек
- FastAPI — REST API поверх ML-пайплайна
- HuggingFace `transformers` — загрузка моделей
- `python-docx` — чтение/запись `.docx`
- `pdfplumber` или `PyMuPDF (fitz)` — извлечение текста и координат из PDF
- LibreOffice в headless-режиме (`soffice --headless --convert-to docx`) — конвертация `.doc` → `.docx` перед обработкой (самый практичный вариант, не изобретайте парсер `.doc` с нуля)
- `pika` или `aio-pika` — подключение к RabbitMQ

### Выбор модели перевода
| Модель | Плюсы | Минусы |
|---|---|---|
| **NLLB-200 (distilled, 600M)** | 200+ языков, одна модель на все пары, хорошее качество | Тяжелее MarianMT, нужнее GPU для скорости |
| **MarianMT (Helsinki-NLP)** | Лёгкие, быстрые, много готовых пар языков | Модель под каждую пару языков — сложнее менеджмент |

**Рекомендация**: начните с NLLB-distilled-600M — одна модель закрывает почти все языковые пары, что сильно упрощает архитектуру. Если не хватит скорости на CPU — рассмотрите MarianMT для самых частых пар (en-ru, en-de, ru-en).

### Пайплайн обработки документа
```
1. Определить формат файла (docx / doc / pdf)
2. Если doc → сконвертировать в docx через LibreOffice
3. Если docx:
   - Пройтись по всем "runs" (фрагментам текста с одинаковым форматированием)
   - Собрать текст на уровне параграфа (runs могут дробить одно предложение!)
   - Перевести
   - Разложить переведённый текст обратно по runs (см. раздел 5 — это ключевая сложность)
4. Если pdf:
   - Извлечь текстовые блоки с координатами (pdfplumber даёt bbox)
   - Перевести текст каждого блока
   - Либо: (а) наложить новый текст на те же координаты (эвристика, менее точно)
          (б) сконвертировать PDF → DOCX (напр. через pdf2docx), обработать как docx, обратно в PDF
5. Сохранить результат в MinIO
```

### API ML-сервиса
```
POST /translate
  { file_key, source_lang, target_lang, format }
  -> запускает обработку (может быть асинхронно через очередь)

GET /health
```

## 5. Ключевая техническая проблема — сохранение форматирования

Это и есть материал для научной новизны диплома.

**Проблема**: В `.docx` одно предложение часто разбито на несколько `runs` с разным форматированием (например, из-за автозамены, проверки орфографии в Word, ручного форматирования). Если переводить run за runом отдельно — перевод получится бессвязным. Если переводить весь параграф целиком — непонятно, как потом распределить переведённый текст обратно по фрагментам с разным форматированием.

**Подходы для сравнения (это и есть исследовательская часть)**:
1. **Наивный**: переводить каждый run отдельно — быстро, но低 качество на разбитых предложениях
2. **Merge-and-map**: склеить текст параграфа → перевести → эвристически распределить обратно по runs пропорционально длине (простая, но не всегда точная эвристика)
3. **Разметка placeholder'ами**: заменить форматированные участки на маркеры (`{{bold_1}}`), перевести текст с маркерами, затем расставить форматирование по позициям маркеров в переводе — более сложный, но точный подход
4. Для PDF: сравнение прямой замены текста по координатам vs конвертации в docx и обратно

Предложите использовать подход 3 как основной — это даст вам что описать в дипломе как "предложенный метод", с сравнением качества (метрика: доля сохранённого форматирования + BLEU/COMET на переводе) против подходов 1 и 2.

## 6. Контракт между Java и ML-сервисом

Зафиксируйте это в начале работы — сэкономит недели на интеграции:

**Сообщение в очередь (Java → ML)**:
```json
{
  "job_id": "uuid",
  "file_key": "s3://bucket/uploads/uuid.docx",
  "source_lang": "en",
  "target_lang": "ru",
  "format": "docx"
}
```

**Результат (ML → Java, через БД или обратное сообщение)**:
```json
{
  "job_id": "uuid",
  "status": "DONE",
  "result_file_key": "s3://bucket/results/uuid.docx",
  "error_message": null
}
```

Кто пишет в БД статус — Java (слушая очередь ответов) или сам ML-сервис напрямую в PostgreSQL — решите в первую неделю, это влияет на структуру обоих сервисов.

## 7. Frontend

### Стек
- React + Vite
- Готовая UI-библиотека (shadcn/ui или Ant Design) — не тратьте время на кастомный дизайн-система
- Axios/fetch для REST, простой polling для статуса (WebSocket — опционально, если останется время)

### Экраны
1. Регистрация/логин
2. Главная: drag&drop загрузки файла, выбор языка исходного/целевого, кнопка "Перевести"
3. Страница статуса задачи (прогресс-бар/спиннер, poll каждые 2-3 сек)
4. Скачивание результата
5. История переводов (таблица заказов)

## 8. План на 6 недель (при сроке 1.5–2 месяца)

| Неделя | Java | ML | Frontend |
|---|---|---|---|
| 1 | Настройка проекта, схема БД, auth | Настройка окружения, парсинг docx (чтение runs), первый прогон NLLB на тексте | Каркас приложения, экраны-заглушки |
| 2 | Upload API, интеграция с MinIO, очередь RabbitMQ | Пайплайн парсинг → перевод → сборка (без сложного форматирования) | Экран загрузки, выбор языков |
| 3 | Интеграция end-to-end с ML-сервисом через очередь | Реализация подхода с placeholder-разметкой (раздел 5) | Экран статуса, поллинг |
| 4 | Обработка ошибок, статусы, история заказов | PDF-пайплайн, тесты качества (BLEU/COMET) | История переводов, скачивание файла |
| 5 | Тестирование, багфиксы интеграции | Сравнение подходов форматирования, метрики для диплома | Полировка UI, обработка ошибок на фронте |
| 6 | Буфер, деплой (Docker Compose) | Финализация экспериментов, графики для диплома | Финальное тестирование |

Если срок реально 1 месяц — сокращайте до docx-only (без .doc и .pdf) и 3-4 языковые пары, PDF и .doc оставьте как "future work" в дипломе.

## 9. Деплой (минимальный, для демо)

Docker Compose с сервисами:
```yaml
services:
  frontend      # nginx + собранный React
  backend       # Java Spring Boot
  ml-service    # Python FastAPI
  postgres
  rabbitmq
  minio
```
Этого достаточно для защиты диплома и демонстрации — не нужен Kubernetes и облачный деплой, если только не останется время.

## 10. Структура диплома (баланс наука/продукт)

1. **Введение** — актуальность (рост объёма документооборота между языками, недостатки существующих решений в сохранении форматирования)
2. **Обзор существующих решений** — Google Docs Translate, DeepL, Smartcat и т.д., их ограничения
3. **Теоретическая часть** — архитектуры машинного перевода (transformer, NLLB, MarianMT), проблема сохранения форматирования при NMT-переводе структурированных документов
4. **Предложенный метод** — раздел 5 этого документа: подход с placeholder-разметкой, обоснование выбора NLLB
5. **Реализация** — архитектура системы (раздел 2), описание каждого модуля
6. **Экспериментальная часть** — сравнение 2-3 подходов к сохранению форматирования, метрики (BLEU/COMET + доля сохранённого форматирования), таблицы результатов
7. **Заключение** — итоги, ограничения, направления развития (PDF с сохранением визуальной вёрстки, больше языковых пар, дообучение на отраслевой лексике)

## 11. Первые практические шаги для команды

1. Зафиксировать контракт API (раздел 6) — сделать это в первый же созвон
2. Каждый поднимает свой сервис локально с заглушками (Java — фейковый статус, ML — эхо-перевод без реальной модели) и проверяет, что все три части друг с другом связываются
3. Только после этого — параллельная разработка каждой части по плану (раздел 8)
4. Общий репозиторий с `docker-compose.yml`, чтобы весь стек поднимался одной командой
